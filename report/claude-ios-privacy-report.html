核心结论

  1. 客户端代码中没有针对 VPN 和真实 IP 的主动探测逻辑 【实锤·未发现】——全二进制无 utun 接口扫描、无 ipify/whatismyip/stun 客户端探测请求。出口 IP 判定完全依赖服务端（TCP 源 IP、CDN 边缘字段）与 Sift 的 IP 侧风控。
  2. 设备身份绑定是全链路的 【实锤】——每个 API 请求携带 Anthropic-Device-ID；登录、会话、内购、积分兑换全流程要求 App Attest / DeviceCheck 证明；存在周期性「会话重证明」（Reattest）机制与专用端点。
  3. Sift Science 商业反欺诈 SDK 完整嵌入 【实锤】——采集设备属性并经 Keychain 持久化设备标识（应用重装不消失），上报至 api3.siftscience.com。应用自己的遥测配置里存在 siftOnly / fraudMonitoring 事件分类，即有专门只送给风控通道的事件。
  4. SIM 卡国家码等运营商信息由 Datadog SDK 采集上报 【实锤】——carrierISOCountryCode / mobileCountryCode / radioAccessTechnology / carrierAllowsVOIP 字符串紧邻 Datadog SDK 代码区，随 RUM 会话上报 us5.datadoghq.com。这意味着即使走 VPN，SIM 归属地仍会出现在遥测里。
  5. 位置采集克制 【实锤】——仅申请「使用期间」定位；CLLocationManager/CLGeocoder 是助手的位置工具（用户主动触发）；无常驻后台定位。另有按国家触发的 Yoti 年龄验证流程。
  6. 封禁判定不在 App 内：App 是信号采集端，判定在服务端——同一台设备上换账号，会经 DeviceCheck（硬件级、服务端可写 2 bit 标记）、App Attest 密钥、Keychain 残留标识、Sift 设备图谱在服务端重新关联 【推断】。

① VPN 检测

Claude 自身代码无 VPN 专项检测 【实锤·未发现】。全程序反编译（68.9 万函数）后，仅有的 2 处 getifaddrs 调用者已定性并归属 Google Maps SDK 静态链接区段：一个是「是否蜂窝网络」布尔判定（接口名前缀 pdp_ip，见反编译章节①），一个是本地 IPv4/IPv6 地址枚举器（见②）——均服务于地图网络分类，结果流向 Google；utun 字符串只出现在 LiveKitWebRTC 框架（语音模式 WebRTC 标准网络枚举）。Claude 请求路径上没有任何 VPN/代理探测。VPN 判定实际来自：服务端 IP 信誉、IP 与时区/语言/SIM 的一致性校验、Sift 的 IP 侧数据 【推断】。

② 时区

无「读取时区并主动上报给 claude.ai」的专用请求字段 【实锤·未发现】，但时区经两条路流出：Firebase GoogleDataTransport 上传时区偏移（GDTCORClockTimezoneOffsetSeconds、"Reading timezone offset" 日志串）【实锤】；Datadog RUM 明确写入时区偏移——反编译确认 [obj setTimezoneOffsetSeconds:]（0x105903140）、[NSTimeZone systemTimeZone]（0x10590b700）、secondsFromGMT（0x1058eff00）三个采集点 【实锤】；Sentry 会话上下文按 SDK 标准行为携带语言环境 【推断】。此外服务端可对比请求时间与出口 IP 所在地时区（无需客户端上报）。

③ 时间

DatadogNTPDateProvider 用 NTP 服务器校准事件时间 【实锤】，客观上可检测本地时钟篡改；隐私清单声明 SystemBootTime 访问（35F9.1，运行时长测量）；全部遥测事件携带客户端时间戳。

④ 位置

仅 NSLocationWhenInUseUsageDescription，无 Always/后台定位 entitlement 【实锤】。ClaudeTools.LocationManager / CoreLocationService / CLGeocoder 是助手的位置工具（用户在对话中触发）；Google Maps/Places 在使用地图功能时采集；注册手机验证流程收集国家码（用户选择器）；Yoti 年龄验证按国家启用。（勘误：geo.region.iso_code 是 OpenTelemetry 语义约定字段表、policyCountryCode 是 Google Maps proto 字段，均非 Anthropic 采集项。）

⑤ 真实 IP 探测

无客户端主动探测 【实锤·未发现】：全二进制无 ipify/icanhazip/ipinfo/whatismyip 类请求；请求头构建函数中也没有任何 IP 字段。不需要——每个 HTTPS 请求的 TCP 源 IP 就是服务端看到的 IP。X-FORWARDED-FOR / clientIp 字符串属于 Google Maps SDK。唯一可能绕过 VPN 的客户端路径是语音模式 WebRTC：ICE 候选若走 UDP/IPv6 而 VPN 不覆盖，LiveKit 媒体服务器可见真实地址 【推断】。

① 蜂窝网络检测（专属函数）

独立布尔函数：遍历系统网络接口，任一接口名以 pdp_ip 开头（iPhone 蜂窝数据接口）即返回真。位于 Google Maps SDK 静态链接区段（0x104–0x105 区间，与 geo.region.iso_code、GMSPaint 同域）。

bool FUN_1055439e8(void) {
    ifaddrs *list = 0;
    if (getifaddrs(&list) == 0) {
        for (ifaddrs *p = list->ifa_next; p != 0; p = p->ifa_next)
            if (strncmp(p->ifa_name, "pdp_ip", 6) == 0) { freeifaddrs(list); return true; }
        freeifaddrs(list);
    }
    return false;
}

② 本地 IP 地址枚举

第二处 getifaddrs 调用者：收集所有「已启用且非回环」（ifa_flags & 9 == 1）接口的 IPv4（inet_ntoa）与 IPv6（inet_ntop）地址，装进数组返回。同样位于 Google Maps 区段。

if (getifaddrs(&list) == 0) {
    arr = [NSMutableArray new];
    for (ifaddrs *p = list; p; p = p->ifa_next) {
        if ((p->ifa_flags & 9) == 1) {           // IFF_UP 且非 IFF_LOOPBACK
            if (p->ifa_addr->sa_family == AF_INET)
                [arr addObject:@(inet_ntoa(...))];   // IPv4
            else if (p->ifa_addr->sa_family == AF_INET6)
                [arr addObject:@(inet_ntop(...))];   // IPv6
        }
    }
}

③ 请求头构建函数（0x100ababe8）

构建发往 claude.ai/api 的全部自定义头。三个此前未定的细节在伪代码里全部落定：

  • 每请求随机 UUID：Foundation.UUID → uuidString → lowercased() 插入字典（对应 X-Client-Request-Id）
  • X-Authorization 头（从机器码字面量解码，0x726f687475412d58 = "X-Author"）：授权路径下由上下文标志位（+0x48）控制添加
  • Geo-Region 兜底值是硬编码 "US"：Swift 小字符串字面量（0x5355 = "US"，判别码 0xe2）直接传入 Geo 插入助手
// 插入助手：键长 0x13 = 19 = "X-Client-Geo-Region"（来自字面量池）
void FUN_100abb928(str value) { dict["X-Client-Geo-Region"] = value; }
...
FUN_1001b63bc("Anthropic-Device-ID");       // 设备 ID 头（持久化 UUID）
UUID().uuidString.lowercased();              // 每请求新随机 ID
if (ctx->flag48) {
    if ((v = FUN_100abba6c()) != nil)

封号维度：对中国用户场景的执行架构分析

本章仅描述逆向可见的信号采集与身份关联架构（系统如何工作），不构成任何规避指引。所有封号规则、阈值与策略均不可见——它们完全在服务端。

结论一：客户端零封号逻辑，判定 100% 在服务端

  • 全二进制没有任何本地封号/停用/地区封锁文案（搜遍 banned/suspended/violation/unsupported-country 等，无一命中用户可见字符串）——封号提示全部由服务端接口动态下发 【实锤·未发现】
  • 客户端没有任何"地区不允许"的本地判断分支；唯一的地理字段 X-Client-Geo-Region 是服务端算好下发、客户端缓存回传的（缺省兜底 "US"，见反编译章节③）——即地理判定本身就在服务端完成 【实锤】
  • App 完整支持简体中文本地化（zh-Hans）——客户端层面并不区分/排斥中国用户 【实锤】

结论二：能指向"中国用户"的信号清单（及 VPN 下的可见性）

信号采集路径走 VPN 时是否仍暴露证据
TCP 出口 IP服务端直接可见（CDN 边缘 + 信誉库）VPN 出口 IP 本身成为新信号（机房 IP 信誉、ASN 类型、与手机号/时区不一致性）推断
SIM 卡国家码（中国移动/联通/电信 = CN）Datadog RUM carrierISOCountryCode/mobileCountryCode（0x1058dec00 等）是——VPN 不改 SIM，遥测会话里 CN 运营商与时区、出口 IP 并存实锤
时区偏移（Asia/Shanghai = +28800s）Datadog setTimezoneOffsetSeconds: + Firebase GDT 时钟数据是——跟随系统设置实锤
语言/地区格式Sentry 上下文（SentryLocale）、系统 Locale是——跟随系统设置实锤存在
手机号国家码（+86）注册手机验证流程（PhoneNumberKit 国家码选择器 + onboarding.phone_verification.* 事件）是（号码本身即归属地）实锤
支付地区内购收据 + App Attest 绑定（ios_iap_receipt_app_attest）；Apple ID 账单地区随收据可见是（收据不因 VPN 改变）机制实锤 地区可见性推断
语音模式真实 IPWebRTC ICE 候选（UDP/IPv6 绕过不覆盖的 VPN）可能暴露推断
地区感知年龄验证Yoti（_isCountryAwareAgeVerificationEnabled）——按国家触发的身份核验是（按账号地区策略触发）实锤

要害在一致性校验：任一信号单独存在都可解释，而「出口 IP 在海外 + SIM 是 CN 运营商 + 时区 +0800 + 系统中文 +86 号码 + 海外 Apple ID 收据」的组合在服务端遥测里是一行完整的矛盾记录。客户端不需要"检测 VPN"——服务端把不一致直接算出来了。

结论三：封号为什么会"跟设备走"——五层持久身份关联

① App Attest 硬件密钥→ ② DeviceCheck 2-bit 服务端标记→ ③ Sift 钥匙串标识（重装不消失）→ ④ __Host-ant_trusted_device Cookie→ ⑤ Anthropic-Device-ID 请求头
  • ① App Attest：Secure Enclave 级密钥，登录/会话/内购/积分全流程断言（LoginAttestation、SessionReattest、bind_attestation）。同一台设备换多少账号，断言都出自同一把硬件密钥 【实锤】
  • ② DeviceCheck：苹果为每台设备保留 2 bit 的服务端可写标记，Anthropic 可读写且跟随物理设备（换 Apple ID、卸载重装都跟随）——天然适合做"此设备已被标记"的持久位 【机制实锤】 【用作封禁标记为推断】
  • ③ Sift：钥匙串里的设备标识 + 首次 IDFV（com.sift.initial_device_ifv）——iOS 卸载 App 不清 Keychain，标识跨安装存活；Sift 平台侧据此做多账号设备图谱关联 【实锤】
  • ④⑤ Cookie 与 Device-ID：可信设备 Cookie 与每次请求的 Anthropic-Device-ID 把账号-设备-会话三元组钉死；App 还原生支持同机多账号（session.activeAccountId），同设备账号天然可关联 【实锤】

这就是"换号又被封"现象的架构解释：新账号注册那一刻，登录证明（App Attest）+ Sift 设备标识 + DeviceCheck 位就会把这台设备的历史带回来。重新证明机制（SessionReattest 周期性挑战 + RotateReattestCredential 轮换）保证会话中途换环境也会被重新钉住设备身份。

风控决策点时间线（服务端消费这些数据的位置）

注册：手机验证 + 国家码→ 登录：LoginAttestation + Sift deviceProperties→ 会话：bootstrap 下发 Geo-Region + Reattest 周期挑战→ 使用：RUM/遥测流（SIM+时区+locale+行为）→ 支付：收据 + App Attest 断言

遥测事件有专用风控分类（siftOnly / fraudMonitoring / fatalEvents / monitoringClient），即部分事件只进反欺诈通道，不进产品分析。

诚实的边界（静态逆向看不到的东西）

  • 规则本身不可见：封号阈值、风险评分权重、IP 库、Sift 评分、哪些组合触发人工审核——全部在服务端，二进制里一行都没有
  • 本报告无法证明某具体信号（如 SIM 国家码）被用于封号决策——只能证明"被采集、被上报、进了风控通道"这一整条链路存在
  • 同为"被封"的账号，具体原因可能各不相同（付款方式、手机号、设备历史、使用模式），不做归因断言
  • 更正记录：早期版本提及的 policyCountryCode 经邻域复核属 Google Maps proto 字段；StFraudAbuseInfo/YetiAbuse 属 Google proto 类型群——均非 Anthropic 风控组件，已从结论中剔除

分析方法

  • 解包 IPA → Payload/Claude.app；plutil 解析 Info.plist / entitlements / GoogleService-Info.plist / PrivacyInfo.xcprivacy
  • nm -u 导入符号能力图（getifaddrs、CTTelephonyNetworkInfo、DCAppAttestService、SCNetworkReachability 等 10,586 项）
  • strings 全量字符串（412,784 条）+ otool -ov ObjC 类方法表交叉定位
  • otool -tV 全反汇编 853MB，literal pool 注释追踪请求头构建函数（0x100abac64–0x100abb0b0）与 getifaddrs 调用者归属
  • Ghidra 12.1.4 headless（JDK 21）全量自动分析：688,893 个函数、7190 秒、2.1 GB 程序库；定向导出 41 个安全相关函数的 C 伪代码（字符串引用追踪 + 导入符号调用者追踪 + 指定地址）

局限性

  • 静态分析 ≠ 运行时观测：未动态抓包验证字段实际取值
  • App Store 签名二进制无本地符号，函数名为地址名；模块归属依据地址区间、字符串邻域与源码路径断言
  • Ghidra 排障记录：ObjC 元数据分析器因类型编码缺陷崩溃（已禁用，Ghidra 12 中名为 "Objective-C Type Metadata Analyzer"）；Swift 解串器逐符号派生进程过慢（已禁用）；-analysisTimeoutPerFile 单位为秒
  • 第 1 处 getifaddrs（0x10459a984）所在库无符号无字符串，归属未定；第 2 处已确定属 Google Maps SDK
